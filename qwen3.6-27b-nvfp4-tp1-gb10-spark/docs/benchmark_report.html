  • NVFP4 权重在本机（SM121 无原生 FP4 计算单元）走 Marlin weight-only kernel，compute 密集场景性能打折属预期；此数据即为该路径下的实际水平。
  • MTP=3 投机解码收益实打实：平均接受长度 2.91–3.58（跨档均值），单请求深稳态接近满接受。
  • TTFT 对输入长度敏感（GB10 算力有限，prefill 是短板）：1K 输入 0.84 s、4K 至 12.48 s、8K 至 22.66 s（均为并发 4 P95）。

3. 测试方法

项目口径
工具vllm bench serve（vLLM 官方，openai-chat 后端，endpoint /v1/chat/completions）
压测客户端位置独立 Linux 服务器远程打被测机（压测流量不占用被测机 CPU/内存，排除客户端干扰）
数据集random（固定输入/输出 token 数，range-ratio=0）
并发定义burst：请求数=并发数、request_rate=inf，全部请求同时发出
输出长度--ignore-eos，每请求输出精确到目标值（1024/4096/8192）
输入 tokens表中为实测值：chat 模板占用导致略低于目标（如目标 4K 实测均 3893、8K 实测均 7766）
热身正式测试前 3 次热身请求，排除 JIT/warmup 冷启动污染
指标口径全部取自工具输出 JSON 官方字段；除 TTFT 由 ms 换算为 s（÷1000）外，其余数值均为官方原值

4. 测试数据（3 组 9 档，按输入/输出组合分表）

TTFT 各列已由官方输出的 ms 换算为 秒 s（÷1000）；Mean TPOT 保持官方 ms 原单位。总/均 = 全部请求合计 / 每请求平均（实测值）。每组并发梯度 1/2/4。

4.0 指标含义

列含义
并发该档 burst 同时发出的请求数（等于该档总请求数，全部同时开跑）
成功 / 失败该档完成 / 失败的请求数（Successful requests / Failed，官方字段 completed/failed）
输入 tokens 总/均全部请求实际输入（prompt）token 合计 / 每请求平均——实测值，非目标值
输出 tokens 总/均全部请求实际输出（completion）token 合计 / 每请求平均——实测值；ignore_eos 下精确等于目标值
Duration s该档整段测试耗时：从第一个请求发出到最后一个请求完成（Benchmark duration，官方字段 duration）
Request throughput (req/s)成功请求数 ÷ Duration，每秒完成的请求数（官方字段 request_throughput）
Output tok/s输出 tokens 总量 ÷ Duration，整机每秒产出的生成 token 数（官方字段 output_throughput），衡量生成吞吐
Mean TTFT (s)首 token 延迟平均值：从发出请求到收到第 1 个生成 token 的耗时（Time To First Token）
P50 / P95 TTFT (s)首 token 延迟的 50 / 95 分位——50%/95% 的请求快于该值；P95 是尾延迟常用指标
Mean TPOT (ms)首 token 之后平均每个输出 token 的耗时（Time Per Output Token），决定稳定吐字速度；单流速度 ≈ 1000 ÷ TPOT
MTP 接受率 %投机解码 draft token 被主模型接受的比例（越高加速越好）
MTP 接受长度每轮投机平均被接受的 token 数（含 1 个真 token；MTP=3 理论上限 4.0）

5. 关键观察

  • 单流速度：26–30 tok/s（TPOT 32–37 ms），随并发数增加 TPOT 基本稳定（decode 未过载），并发 4 聚合吞吐 78–86 tok/s。
  • MTP 表现好：档均值接受率 63.5–85.9%、接受长度 2.91–3.58；被测机服务日志显示单请求稳态段接受率 96.9%、平均接受长度 3.91（MTP=3 上限 4.0），长输出场景投机解码收益显著。
  • prefill 是短板：GB10 算力有限（启动日志 "Not enough SMs to use max_autotune_gemm"），8K 输入并发 4 的 P95 TTFT 达 22.66 s；重输入业务建议关注 TTFT 或考虑 prefill 侧优化。
  • NVFP4 走 Marlin：SM121 无原生 FP4 计算单元，权重以 weight-only Marlin kernel 运行，GEMM 密集阶段打折——本报告数据即该路径实际水平，与原生 FP4 硬件（如 B200）不可直接类比。

6. 数据边界与备注

  • 测试范围（用户指定）：仅 1K→1K、4K→4K、8K→8K 三组 × 并发 1/2/4；4K→32K、8K→32K 两组及各组的 16/32/64 高并发档未测试，本报告为部分矩阵。
  • KV cache 为 fp8_e4m3（NVFP4 checkpoint 自带配置，非启动参数），attention 后端 FlashInfer（xqa decode）。
  • prefix caching 虽在启动参数中开启，但被 MTP+Mamba 混合架构自动禁用（启动日志 WARNING：无法识别 draft 组，跨请求前缀复用不可用）——多轮会话场景无前缀命中收益。
  • gpu-memory-utilization 0.95 为本机实际上限：0.96/0.98 均无法完成启动（激活/CUDA graph 峰值余量不足）。
  • 测试数据为 random 数据集随机 token；并发为 burst 全同时发出，不含错峰/限速场景。
  • 原始数据（逐请求 input_lens/output_lens/ttfts 等）: 压测机本地 /root/qwen27b-bench/results-spark44/（9 个 JSON + 逐档 log）。
