5. 服务崩溃记录（两次，如实）

5.1 第一次：并发 32 时 DFlash2 speculator OOM（初始配置）

  • 初始配置 max-num-seqs 512 / util 0.9；1K 组 c1~c16 正常，c32 档 32 请求卡死约 40 秒后 8 卡同时 OOM，服务死亡；c64 及其后全部档位连坐失败。
  • 根因（源码级定位）：dflash/speculator.py 的 propose() 中 torch.cat(aux_hidden_states) 动态工作区（约 924 MiB/次，大小 ∝ 并发 × spec 深度）不计入 vLLM 显存规划，叠加 1.18 GiB 分配器碎片。
  • 修复（三项）：PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True（消碎片）+ max-num-seqs 512→64（压峰值激活）+ util 0.9→0.85（留余量）。修复后 c32/c64 全部通过。

5.2 第二次：8K×c16 长负载下 worker RPC 超时

  • 修复配置下 1K/4K 全组 + 8K c1~c4（共 14 档）通过后，8K×c16 档 worker 的 sample_tokens RPC 超时（EngineCore 判死），服务再次死亡；其后 12 档全部连坐失败。无 OOM 记录——与第一次不同死因。
  • 两次崩溃点均在 DFlash2 投机路径（speculator propose / sample_tokens），发生于并发 ≥16~32 或长输出高负载场景。本报告为该平台该组合的当前能力边界，待 vLLM 上游修复后可补测 12 个缺失档与 Agent 场景组。

6. 结论

  • 单流 decode：15.5~20.9 tok/s（TPOT 46.6~64.0 ms）——随机 token 口径。
  • 聚合吞吐：1K 组 c1→c64 从 20.6 升至 97.5 tok/s，但 TPOT 从 46.6 恶化至 480.1 ms、TTFT 至 88.5 s；4K×c32 TTFT 达 171.2 s——高并发延迟是主要短板。
  • DFlash2 投机：接受率 15.4~27.9%、接受长 2.08~2.96（上限 8.0），Drafted ≈ 4×Accepted——深度 7 的 draft 大部分被拒，投机收益有限。
  • 稳定性边界：两次崩溃（OOM / RPC 超时）均发生在 DFlash2 投机路径高并发段；有效数据覆盖 14/26 档。

7. 数据边界与备注

  • 测试范围：26 档矩阵中 14 档有效（1K 全组 6 档 / 4K 全组 5 档 / 8K 组 c1~c4）；8K c16/c32 与两个 32K 长输出组（10 档）因第 5 节第二次崩溃未获得数据；Agent 任务流场景组未测（服务崩溃在前）——待稳定性解决后补测。
  • 失败档的 JSON 记录 0 成功/全失败，未列入数据表；bench 侧错误（Internal Server Error / Connection refused）与服务端日志互证。
  • 接受率/接受长/Accepted/Drafted tokens 均取自服务端 SpecDecoding 周期日志按档位 START/DONE 时间窗归集（服务端口径，与压测工具指标体系相互独立）。
