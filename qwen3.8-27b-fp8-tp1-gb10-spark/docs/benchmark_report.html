Qwen3.8-27B-FP8（官方包）DGX Spark（GB10）单机 TP1 压测报告

基于 vLLM 官方基准工具 vllm bench serve 的部分矩阵测试，含同机三方对照（Qwen3.6-NVFP4 官方包 / Qwen3.8-NVFP4 unsloth 包 / 本报告 FP8 包）。指标名称、单位与工具官方输出保持一致。

报告日期：2026-09-03 硬件：DGX Spark（GB10，SM121，121G 统一内存） 模型：Qwen3.8-27B-FP8（TP=1，MTP=3） vLLM nightly 0.28.1rc1.dev283 范围：3 组 9 档（部分矩阵）+ 三方对照

1. 测试结论

测试档位
9/9 全部成功

3 组输入/输出组合 × 并发 1/2/4，零失败

单流 decode
14–17 tok/s

TPOT 58–78 ms，三方对照中最慢

三方排序（实测）
NVFP4官方 > NVFP4unsloth > FP8

FP8 比 unsloth-NVFP4 再慢 17~36%

MTP 接受率
45.4–76.8%

接受长度 2.36–3.30

  • 意外结论：官方 FP8 包在 GB10 上是三个方案中最慢的（吞吐 14–52 tok/s），比 unsloth NVFP4 再低 17~36%、比官方 NVFP4 包低 39~48%。
  • 根因一（主）：该 FP8 包的 KV cache 为 bf16（未量化）——启动日志 kv_cache_dtype=auto 且 KV 容量仅 101 万 token（三方最小）。decode 每 step 读全部 KV，bf16 的读取数据量是 fp8 KV 的 2 倍，带宽密集的 decode 直接受累（TPOT 58–78 ms 三方最差）。
  • 根因二：GEMM 走 CutlassFp8BlockScaled kernel（非 Marlin/FlashInferFP8），且平台提示 "Not enough SMs to use max_autotune_gemm"——SM121 上该 kernel 效率一般。
  • 外部观点修正：MiaAI-Lab issue #186 所说 "fp8 fits very well" 指其 DeepSeek 栈（dspark 用 nvfp4_ds_mla 量化 KV），不能外推到 Qwen 官方 FP8 包（其 KV 恰为 bf16）。

  • TPOT 与 KV dtype 强相关：KV fp8 的 A（32~41ms）< KV fp8 的 B（41~61ms）< KV bf16 的 C（58~78ms）——decode 带宽随 KV 每字节翻倍而恶化的规律清晰可见。
  • 本机跑 Qwen 的实测排序：官方 NVFP4 包 > unsloth NVFP4 > 官方 FP8；Qwen3.8 在 GB10 上当前最优解是 unsloth-NVFP4。
  • 待验证项：FP8 + --kv-cache-dtype fp8（KV 带宽减半，预期 TPOT 改善；需注意 attention 后端可能切换）。

6. 数据边界与备注

  • 测试范围：仅 1K→1K、4K→4K、8K→8K × 并发 1/2/4（部分矩阵）；4K→32K、8K→32K 及 16/32/64 高并发档未测。
  • KV cache bf16 为该官方 FP8 checkpoint 自带行为（非启动参数指定）；如需 KV 量化需显式传 --kv-cache-dtype fp8（未在本轮测试）。
  • 权重以本地目录方式加载（~/Qwen3.8-27B-FP8 平铺结构）。
  • prefix caching 虽开启但被 MTP+Mamba 架构自动禁用（三个方案一致）。
  • 结论适用范围：SM121（GB10）+ vLLM nightly 0.28.1rc1；不代表原生 FP8 硬件（B200/GB300 等）上的表现。
  • 原始数据：压测机本地 /root/qwen27b-bench/results-spark44-fp8/（9 个 JSON + 逐档 log）；对照 results-spark44/、results-spark44-qwen38/。
