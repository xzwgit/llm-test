1×GB10 · Qwen3.8-27B（RadixArk NVFP4）· SGLang DSpark 压测报告

1. 概述

被测配置：DGX Spark（单机单卡 GB10，121GB 统一内存）· SGLang 官方 Qwen3.8-27B 专用镜像（lmsysorg/sglang:qwen38-27b，版本 0.0.0.dev0+qwen38.27b.g561c8f3）· 主模型 RadixArk/Qwen3.8-27B-NVFP4（modelopt_mixed 量化，权重 22.17GB）· 投机解码 DSPARK（draft：RadixArk/Qwen3.8-27B-DSpark，3.38GB；请求 num-steps=5 被镜像强制覆盖为 1，实际按 num_steps=1 + num_draft_tokens=8 运行）· KV cache fp8_e4m3 · attention-backend flashinfer · 256K 上下文
  • 随机 token 标准口径（vllm bench serve，官方工具）：单请求 decode 21.6 ~ 35.8 tok/s（TPOT 27.6~46.0 ms）；并发 4 聚合输出吞吐 45.9 ~ 69.1 tok/s，最高出现在 8K→8K × 并发4（69.1 tok/s）。
  • 真实文本单流（chat 请求，中文/英文/代码 × 开/关思考共 5 组）：decode 16.9 ~ 28.6 tok/s。
  • 投机解码未达预期：全程（随机与真实文本）服务端日志口径接受率仅 0.13~0.24、平均接受长度 1.9~2.7（5 步理论上限 6），draft 验证开销未能转化为足够接受 token，是单流速度受限的直接因素之一。
  • TTFT：随机口径 0.51~4.10 s（均值），随输入长度与并发上升。

3. 压测方法

  • 工具：vllm bench serve（官方），backend openai-chat，数据集 random（随机 token），--ignore-eos 强制精确输出长度；指标名/单位与工具原生输出一致。
  • 矩阵：输入→输出 = 1K→1K / 4K→4K / 8K→8K 三组 × 并发（=请求数）1 / 2 / 4，共 9 档；每档前 warmup 3 次。
  • TTFT 已换算为秒（s）；TPOT 为毫秒（ms）；总耗时为该档全部请求完成用时。
  • 指标口径：全部取自工具输出 JSON 官方字段（successful/failed、total_input/output_tokens、duration、request_throughput、output_throughput、mean·p50·p99_ttft_ms、mean_tpot_ms）；除 TTFT 由 ms 换算为 s（÷1000）外，其余数值均为官方原值；接受率/接受长度为服务端日志口径。

3.1 指标含义

列含义
并发该档 burst 同时发出的请求数（等于该档总请求数，全部同时开跑）
成功请求数该档完成 / 失败的请求数（Successful requests / Failed，官方字段 completed/failed；本测试全部成功）
输入 tokens全部请求实际输入（prompt）token 合计——实测值，非目标值
输出 tokens全部请求实际输出（completion）token 合计；ignore_eos 下精确等于目标值
Output token throughput (tok/s)输出 tokens 总量 ÷ Duration，整机每秒产出的生成 token 数（官方字段 output_throughput），衡量生成吞吐
TTFT 均值 / P99 (s)首 token 延迟（Time To First Token）：从发出请求到收到第 1 个生成 token 的耗时；P99 = 99% 的请求快于该值，尾延迟指标（官方字段 mean_ttft_ms / p99_ttft_ms 换算为秒）
TPOT 均值 (ms)首 token 之后平均每个输出 token 的耗时（Time Per Output Token），决定稳定吐字速度；单流速度 ≈ 1000 ÷ TPOT（官方字段 mean_tpot_ms）
总耗时 (s)该档整段测试耗时：从第一个请求发出到最后一个请求完成（Benchmark duration，官方字段 duration）
decode (tok/s)（第 5~7 节场景组）单请求生成速度：输出 tokens ÷（总耗时 − TTFT），流式请求以首 token 时刻分隔
接受率 / 接受长度（服务端日志口径）投机解码 draft token 被主模型接受的比例 / 每轮平均被接受的 token 数，接受率越高加速效果越好（DSPARK 实际配置 num_steps=1、num_draft_tokens=8）

6. Prefix Cache 命中验证与多轮场景（本测试补充项）

方法：同一 13,860 token 长前缀请求连续发送 3 次（max_tokens=1，总时长近似 TTFT），观察服务端 Prefill batch 日志的 #cached-token。

次序输入 tokens服务端 #new-token服务端 #cached-token总时长 ≈ TTFT (s)
第 1 次（冷）13,86013,860（4 次 chunked prefill）06.56
第 2 次（命中）13,8603613,8240.24
第 3 次（命中）13,8603613,8240.22
  • Prefix caching 在本配置下生效：相同前缀重复请求时 prefill 几乎全免（13.8K token 只重算 36 个），TTFT 降低约 27 倍；Mamba/GDN 混合架构的状态缓存与 KV 一并由 radix cache 复用。
  • 加成仅作用于 prefill（TTFT）侧：decode 逐 token 生成速度（tok/s）不受缓存影响。多轮对话/长文档重复问答场景下"开始出字"显著变快，但出字速度仍为第 4/5 节量级。
  • 第 4 节随机 token 口径每次 prompt 互不相同，prefix cache 命中为 0，两者互不冲突。

9. 结论

  • 单流 decode（通用文本）：随机口径 21.6 ~ 35.8 tok/s（TPOT 27.6 ~ 46.0 ms）；真实文本 16.9 ~ 28.6 tok/s。
  • 单流 decode（结构化/模式化输出）：Agent 工具调用 JSON 场景 52.2 ~ 69.0 tok/s（第 7 节），多轮重复模式文本 48 ~ 63 tok/s（第 6.1 节）——本测试单请求最高观测值 69.0 tok/s 出现在此场景，投机解码接受率随输出可预测性上升而转化为速度。
  • 聚合吞吐：并发 4 时 45.9 ~ 69.1 tok/s，最高 69.1（8K→8K × 并发4）；服务端日志口径并发段 gen throughput 峰值 71.3 tok/s。
  • 缓存加成：prefix cache 命中使 TTFT 从 6.56 s 降至 0.24 s（13.8K 前缀、27 倍），Agent/多轮场景 TTFT 稳定在 0.2~0.4 s；热态长前缀场景总吞吐口径 400+ tok/s。缓存只加速 prefill 侧，不改变 decode tok/s。
  • TTFT（冷态无缓存）：1K 输入 0.5~1.2 s；4K 1.4~2.9 s；8K 2.1~4.1 s（chunked-prefill 4096 下 8K 输入需 2 次 prefill）。
  • DSPARK×5 的收益取决于输出可预测性（第 8.1 节对照）：无投机基线 ~12.4 tok/s，投机后结构化输出 4~5 倍（峰值 69.0）、自然语言 1.3~2.7 倍、随机 token 1.7~2.9 倍——均为正贡献。

10. 数据边界与备注

  • 测试范围：1K→1K、4K→4K、8K→8K × 并发 1/2/4，共 9 档随机 token；真实文本单流 5 组；缓存验证 3 次；多轮对话 5 轮；热态长输出 3 组；Agent 任务流 12 轮。4K→32K、8K→32K 长输出组及 8 以上并发未测试（max-running-requests=8）。
  • 随机口径随机性与官方工具一致（random 数据集 + ignore-eos）；TPOT/TTFT P99 取自工具 JSON 原生输出，未做换算。
  • 接受率/接受长度为服务端日志口径（被测服务自行统计），与压测工具指标体系相互独立。
  • 权重为 modelopt_mixed NVFP4 路线。注：GB10 规格标称 1000 TOPS FP4（2:4 稀疏口径，dense 减半），但当前推理软件栈在 SM121 上未提供原生 FP4 计算路径（权重经反量化以 bf16 参与 GEMM）；decode 阶段瓶颈为统一内存带宽（273GB/s），FP4 的实际收益来自权重体积减半而非算力加成。
  • 原始数据：压测机 /root/qwen27b-bench/results-spark44-sglang/（9 个 JSON + 逐档 log）；真实文本脚本 /root/qwen27b-bench/realtext_sglang.py、realtext_nothink.py；缓存验证脚本 prefix_cache_test.py；多轮/热态/Agent 脚本 supplement_a.py、supplement_b_agent.py 及对应 log；服务日志 docker logs sglang-qwen38。
