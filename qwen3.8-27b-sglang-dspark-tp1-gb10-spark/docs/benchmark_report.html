  • 方法：同一 13,860 token 长前缀请求连续发送 3 次（max_tokens=1，总时长近似 TTFT），观察服务端 Prefill batch 日志的 #cached-token。
  • Prefix caching 在本配置下生效：相同前缀重复请求时 prefill 几乎全免（13.8K token 只重算 36 个），TTFT 降低约 27 倍；Mamba/GDN 混合架构的状态缓存与 KV 一并由 radix cache 复用。

9. 结论

  • 单流 decode（通用文本）：随机口径 21.6 ~ 35.8 tok/s（TPOT 27.6 ~ 46.0 ms）；真实文本 16.9 ~ 28.6 tok/s。
  • 单流 decode（结构化/模式化输出）：Agent 工具调用 JSON 场景 52.2 ~ 69.0 tok/s（第 7 节），多轮重复模式文本 48 ~ 63 tok/s（第 6.2 节）——本测试单请求最高观测值 69.0 tok/s 出现在此场景。
  • 聚合吞吐：并发 4 时 45.9 ~ 69.1 tok/s，最高 69.1（8K→8K × 并发4）；服务端日志口径并发段 gen throughput 峰值 71.3 tok/s。
  • 缓存加成：prefix cache 命中使 TTFT 从 6.56 s 降至 0.24 s（13.8K 前缀、27 倍），Agent/多轮场景 TTFT 稳定在 0.2~0.4 s；热态长前缀场景总吞吐口径 400+ tok/s。缓存只加速 prefill 侧，不改变 decode tok/s。
  • TTFT（冷态无缓存）：1K 输入 0.5~1.2 s；4K 1.4~2.9 s；8K 2.1~4.1 s（chunked-prefill 4096 下 8K 输入需 2 次 prefill）。
  • DSPARK 的收益取决于输出可预测性（第 8.1 节对照）：无投机基线 ~12.4 tok/s，投机后结构化输出 4~5 倍（峰值 69.0）、自然语言 1.3~2.7 倍、随机 token 1.7~2.9 倍——均为正贡献。

10. 数据边界与备注

  • 测试范围：随机 token 九档（1K/4K/8K × 并发 1/2/4）；真实文本单流 5 组；缓存验证 3 次；多轮对话 5 轮；热态长输出 3 组；Agent 任务流 12 轮；关闭投机对照 12 轮。长输出（32K）组及 8 以上并发未测试（max-running-requests=8）。
  • 权重为 modelopt_mixed NVFP4 路线。注：GB10 规格标称 1000 TOPS FP4（2:4 稀疏口径，dense 减半），但当前推理软件栈在 SM121 上未提供原生 FP4 计算路径（权重经反量化以 bf16 参与 GEMM）；decode 阶段瓶颈为统一内存带宽（273GB/s），FP4 的实际收益来自权重体积减半而非算力加成。
  • 接受率/接受长度为服务端日志口径（被测服务自行统计），与压测工具指标体系相互独立。九档逐档接受率未留存：无投机对照测试重建了服务容器，随机 token 九档期间的逐档 Decode 日志随旧容器丢失；留存的并发段（0.14~0.20）与真实文本段（0.13~0.24）观察见第 8 节。
  • 随机口径与官方工具一致（random 数据集 + ignore-eos）；TPOT/TTFT P99 取自工具 JSON 原生输出，TTFT 已由 ms 换算为 s。
  • 原始数据：压测机 /root/qwen27b-bench/results-spark44-sglang/（9 个 JSON + 逐档 log）；场景组脚本 realtext_sglang.py、realtext_nothink.py、prefix_cache_test.py、supplement_a.py、supplement_b_agent.py 及对应 log；服务日志 docker logs sglang-qwen38。
